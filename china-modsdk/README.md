# Diorama — China Edition (NetEase) ModSDK scaffold

A **scaffold**, not a finished product: the Python client/server module layout,
the projection/tile-baking/waypoint/radar core, and the JSON UI templates for
bringing [Diorama](../../README.md) to 《我的世界》中国版 as a **NetEase ModSDK
mod** (Python 2.7 scripts + Bedrock JSON UI).

It is built for **personal PC development-workbench testing**: everything that
can be exercised without the game — the map maths, the waypoint store, the radar
classification, the UI-JSON consistency — runs on a plain PC under CPython, and
the parts that need the engine are isolated behind small adapters and wrapped so
a missing engine call degrades instead of crashing.

> **Nothing here has been run inside the China Edition client.** The API calls
> are based on the public ModSDK documentation and community references, but
> several of them are *unverified* — see [Unverified API
> assumptions](#unverified-api-assumptions) and
> [`docs/API_ASSUMPTIONS.md`](docs/API_ASSUMPTIONS.md). Treat every `mod.*`
> import as a hypothesis to check against your build.

`bedrock-addon/` is untouched by this scaffold and is a separate deliverable.

## 1. What the ModSDK can and cannot do

The Fabric mod is a **client-side renderer**. The China Edition ModSDK lets a
script read the world, talk over a network channel and drive **JSON UI**, but it
does not let a script upload a texture it computed at run time. The mapping is
therefore deliberately honest — no fake approximations:

| Fabric mod feature | ModSDK scaffold | State |
|---|---|---|
| Angled voxel projection, sun/AO/sky-occlusion shading, water depth, mipmaps | `modCore.baker` — pure Python, ported from `TileBaker.java`, fully unit-tested and previewable on PC | ✅ implemented |
| Baked tiles served live to the client | Server bake service with a queue + budget; **refuses by default** because a 128×128-ray tile is seconds of Python on the game thread. The full-screen map uses an atlas baked offline by `tools/bake_atlas.py` | ⚠️ opt-in |
| "What block is under this map pixel" | `modCore.pick` + server pick service; this is what makes tap-to-place-waypoint land on the ground | ✅ |
| Waypoints (add / edit / colour / share / import / death marker) | `modCore.waypoint` + `WaypointStore` (the Java port's tolerance rules intact) over `CreateConfig` local storage; server relays shares in chat | ✅ |
| Radar for players and mobs | Server scans and classifies (`modCore.radar` tables), pushes projected blips to the client | ✅ |
| Minimap, full-screen map, settings | JSON UI (`resource_pack/ui/*.json`) + `ScreenNode` subclasses | ✅ templates |
| Compass, coordinates, biome readout | HUD screen, refreshed on a timer | ✅ |
| Engine-drawn minimap with markers | `MiniMapBaseScreen` is used **if the build exposes it** (documented as experimental); otherwise the HUD falls back to the static atlas + labels | ⚠️ build-dependent |
| Cave slices, fair-play fog of war, spawn overlays | Supported by the baker/pick APIs (`fog_of_war`, cave `layer`); the settings screen exposes them | ⚠️ partial |
| Live re-bake on block edits | Not wired: tiles are baked on request, not invalidated per edit | ❌ not yet |

## 2. Directory layout

```
china-modsdk/
├── DioramaMod/                        # the folder the launcher installs
│   ├── diorama_behavior_pack/
│   │   ├── manifest.json              # data module
│   │   ├── entities/                  # required by the ModSDK, empty otherwise
│   │   ├── pack_icon.png
│   │   └── dioramaScripts/            # the Python the engine loads
│   │       ├── modMain.py             # @Mod.Binding / InitServer / InitClient
│   │       ├── modCommon/             # namespace, event names, logging
│   │       ├── modCore/               # PURE python: no `mod.*` import at all
│   │       ├── modServer/             # system, components, engine adapters
│   │       └── modClient/             # system, components, UI screens, adapters
│   └── diorama_resource_pack/
│       ├── manifest.json
│       ├── ui/                        # JSON UI: _ui_def.json + 5 screens
│       ├── texts/{zh_CN,en_US}.lang   # JSON language files
│       └── textures/ui/*.png          # generated by tools/gen_textures.py
├── tools/                             # PC workbench: no game needed
│   ├── validate.py                    # manifests, UI, texts, paths, purity
│   ├── gen_textures.py                # all UI textures + pack icons
│   ├── preview_bake.py                # bake a preview PNG
│   └── bake_atlas.py                  # bake the atlas that ships in the pack
├── tests/                             # 277+ unit tests over modCore
├── docs/{API_ASSUMPTIONS,ARCHITECTURE}.md
└── README.md
```

## 3. PC development-workbench workflow

Everything below runs on a plain PC, with no game and no ModSDK:

```sh
cd china-modsdk

python3 tools/validate.py            # manifests, UI, texture refs, control paths
python3 tools/validate.py --strict   # warnings fail too

python3 run_tests.py -q              # the modCore unit suite
cd tests && python3 test_baker.py    # one module

python3 tools/gen_textures.py        # write the UI textures and pack icons
python3 tools/preview_bake.py --grid 2 --samples 1 --overlay waypoints \
        --out docs/preview_waypoints.png
python3 tools/bake_atlas.py --grid 2 --samples 1   # the shipped map atlas
```

`docs/preview_waypoints.png` is the regression picture: a stitched 2×2 tile bake
of the deterministic `SyntheticWorld`, with a keep, trees, terrain undulation and
waypoint/radar markers drawn on top. If a change to the projection or the
shading breaks something, that image changes.

Installing on the game side (when you are ready to test in the client):

1. Download the **Mod PC 开发包** (developer build) and register as a developer.
2. Put `DioramaMod/` anywhere convenient and point the developer `addon.json`
   next to `Minecraft.Windows.exe` at it:
   `{"install": ["<path>/DioramaMod"], "use": {"<levelID>": ["DioramaMod"]}}`.
3. Launch, open the console, and filter for the `[diorama]` prefix. Every
   callback is wrapped, so a failure shows up as one log line, not a crash.
4. `diorama` in chat prints the command list (`add`, `list`, `map`, `radar`,
   `pick`, `share`).

## 4. Unverified API assumptions

These are the calls the scaffold makes that the public documentation does **not**
fully pin down for the build this targets. Each one is used through a guarded
helper (`getattr` / `try`) with a documented fallback, so an incorrect guess
should degrade rather than throw. `docs/API_ASSUMPTIONS.md` lists the exact
symbol, the guard and the fallback for every row.

| # | Assumption | Used in | Fallback if wrong |
|---|---|---|---|
| 1 | `RegisterSystem(namespace, name, "pkg.module.Class")` takes a **string class path**. (One API reference page says `cls:class`; official guides and community frameworks use the string.) | `modMain.py` | If your build wants a class, replace the string constant in `modCommon/modConfig.py`; nothing else changes |
| 2 | `clientApi.RegisterUI(ns, key, cls, "<namespace>.<file>")`, with `uiScreenDef` = `diorama.diorama_hud` | `modClient/DioramaClientSystem.py` | Try `"<file>"` alone, or the file/namespace-identical form |
| 3 | The `ScreenNode` base class comes from `clientApi.GetScreenNodeCls()`. Older code uses `GetUIScreenCls()`. | `modClient/ui/ui_base.py` | Tries both, then falls back to `object` so imports still succeed |
| 4 | `MiniMapBaseScreen` is available via `GetMiniMapBaseScreenCls()` and offers `AddEntityMarker` / `AddStaticMarker` / `ZoomIn` / `ZoomOut`. Documented as **experimental**. | HUD design | Falls back to `ScreenNode`; the minimap then shows the static atlas only |
| 5 | Base-screen control paths sit under `/variables_button_mappings_and_controls/safezone_screen_matrix/inner_matrix/safezone_screen_panel/root_screen_panel` | `modCommon/modConfig.BASE_SCREEN_PATH` | `ui_base.resolve()` centralises it — change one constant |
| 6 | `"$screen_content": "diorama.<root>"` puts the screen's content under that wrapper, so paths are `BASE_SCREEN_PATH + "/<root>" + path` | all UI screens | `CONTENT_ROOT` per screen; getting this wrong is the usual cause of "the control API does nothing" |
| 7 | `CreateBlockInfo(levelId).GetBlockNew(pos, dimId)` returns `{"name", "aux"}` and `None` for an unloaded chunk | `modServer/engine/block_source.py` | Treated as "no data" → fog; if it returns `(name, aux)` the adapter needs a tuple branch added |
| 8 | `CreateBlockInfo(levelId).GetBlock(pos)` (client) returns `(name, aux)` | `modClient/engine/client_blocks.py` | Accepts tuple, list and dict shapes; `None` ⇒ no data |
| 9 | `GetBlockLight` / `GetBlockSkyLight` (or `GetSkyLight`) exist on the block component | lighting | Probed once; if absent the baker uses its own ray-based sky occlusion and treats block light as zero |
| 10 | `GetTopBlockHeight((x, z), dimId)` exists on the block component | `top_at()` | Disabled after the first failure; the baker then starts rays at the global `top_y` (correct, slower) |
| 11 | `CreateGame(levelId).GetEntitiesInSquareArea(entityId, start, end)` returns entity ids (or a dict); some builds want it without the leading entity id | `entity_query.py` | Tries both signatures once, then disables the radar with one log line |
| 12 | `CreateEngineType(id).GetEngineTypeStr()` / `IsEntityAlive(id)`, `CreatePos(id).GetFootPos()`, `CreateName(id).GetName()`, `CreateRot(id).GetRot()` | radar/waypoints | Any missing call ⇒ that entity is skipped |
| 13 | `NotifyToClient(playerId, eventName, data)` / `NotifyToServer(eventName, data)` carry a custom event, and the receiver sees the sender as `playerId` or `__playerId` | all networking | Sender id is read from either key; a broadcast path exists for chat |
| 14 | Custom **client → server** events are received by listening on `(namespace, CLIENT_SYSTEM_NAME, event)` | `DioramaServerSystem._listen_client` | If your build routes them differently, this is the one place to change |
| 15 | `OnScriptTickServer` / `OnScriptTickClient` fire automatically **or** can be subscribed to as engine events | tick loops | A `CreateGame(levelId).AddRepeatedTimer(...)` timer is started as well; either path drives the tick |
| 16 | `CreateConfig(localPlayerId).GetConfigData/SetConfigData` persists strings per player | settings + waypoints | Falls back to an in-memory backend (nothing persists) with a warning |
| 17 | `CreateGame(levelId).GetSeed()` / `GetLevelSeed()` exists for a stable per-world key | waypoint folders | Falls back to `"local"`, so all local worlds share one waypoint list |
| 18 | `clientApi.GetScreenSize()`, `PushScreen(ns, key)`, `PopScreen()`, `ScreenNode.Clone/RemoveComponent/GetBaseUIControl(...).asLabel()/asImage()/asButton()` | UI | Every call is guarded; a missing one costs one widget, never the screen |
| 19 | Chat is reachable via `CreateMsg(id).NotifyOneMessage(playerId, line)` (probed names: `CreateChat`, `SendMsg`, `SendMessage`) | share relay | Falls back to an action-bar notice via `EV_NOTICE` |
| 20 | Event payload field names (`message` vs `Message`, `playerId` vs `id`) | events | Both spellings are read where documented sources disagree |
| 21 | The UI definition manifest is `ui/_ui_def.json` (the China guide's name). International Bedrock uses `ui/_ui_defs.json` | resource pack | The validator accepts either and warns; rename or copy the file if your build disagrees |
| 22 | `texts/*.lang` are **JSON** objects (`{"key": "value"}`) | localisation | The validator enforces parseable JSON and matching key sets |
| 23 | The mod namespace may be shared by several UI files (`"namespace": "diorama"` in each), instead of one namespace per file | `ui/*.json` | If your Studio insists on file name == namespace, rename the namespace keys and the `RegisterUI` definitions together; `tools/validate.py` reports unresolved references if you miss one |
| 24 | `CreateBlockInfo` is available server-side for arbitrary loaded chunks | picks | If not, picks fall back to the client-side block source |
| 25 | Python 2.7 is the script runtime (community references state 2.7.18) | all scripts | Every file is 2.7/3-compatible; the tests run under Python 3, and `python2 tests/run_tests.py` is expected to work but is **not** verified here |

## 5. Testing and validation

* `python3 run_tests.py` — 277+ unit tests over `modCore`: projection round
  trips, tile-key flooring/`lod`, palette aux resolution, the baker (flat ground,
  cave slices, saved-pixel merge, progress reporting, mip caching), pick, the
  waypoint store (bad entries, backups, death cap, share-line round trip), radar
  classification/filters/ordering and settings clamping.
* `tests/test_scaffold.py` (run by `run_tests.py`) — parses the two pack
  manifests, checks `_ui_defs.json` against the UI files on disk, that every
  referenced texture exists, that `en_US`/`zh_CN` keys match, and runs
  `tools/validate.py --strict` as a subprocess. It reads the tree instead of the
  core interface, so a renamed control is caught even under `--core my_core`.
* `python3 tools/validate.py --strict` — manifests, UUIDs, versions, module
  types, Python syntax **and** the rule that `modCore` never imports `mod.*`,
  every texture referenced by every UI file existing on disk, every
  `@namespace.control` reference resolving, matching language keys, and — most
  usefully — every control path the Python asks for existing in the JSON.
* `tools/preview_bake.py` / `tools/bake_atlas.py` — visual check of the baker.
